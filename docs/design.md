# 前端设计规范

本规范用于新增页面、调整组件和审查视觉改动，维护 Muchakucha Zwei 的统一设计语言。适用于 Android、iOS 和 Web；移动端是布局与操作体验的首要依据。

本文约定通用规则，不固定具体页面的功能、文案或交互方案。产品需求决定页面行为；本规范决定这些行为如何融入现有界面。

## 设计方向

温暖、清晰、克制。暖白背景承载白色内容面板，珊瑚红突出主要操作，青绿作为有限的辅助色。以字体层级、留白和对齐组织信息，让内容与操作容易辨认。

借鉴 Apple 风格的信息层级与细节一致性，沿用本项目的品牌色和跨平台组件。参考网站或设计截图用于理解方法，不作为整套替换主题的依据。

## 色彩与表面

以下数值用于识别当前视觉基线；代码始终引用对应主题 token。

| 语义 | Token / 当前颜色 | 用法 |
| --- | --- | --- |
| 页面底色 | `canvas` · `#FFF8F2` | 全局暖白背景 |
| 内容表面 | `surface` · `#FFFFFF` | 卡片、表单及阅读区域 |
| 主色 | `coral` · `#B94736` | 主要操作与重点信息 |
| 辅助色 | `teal` · `#277A72` | 次级分类或辅助强调 |
| 正文 | `ink` · `#2D2725` | 标题、正文和主要图标 |
| 次要文字 | `inkMuted` · `#6F625D` | 元信息和辅助内容 |
| 控件边界 | `border` · `#9C877E` | 需要辨识的输入与交互边界 |
| 装饰分隔 | `separator` · `#EDE3DC` | 分组分隔与轻量卡片轮廓 |
| 危险状态 | `destructive` · `#B42318` | 错误与破坏性操作提示 |

浅色强调背景使用 `coralSoft`、`tealSoft` 等配套 token。按下、禁用、链接等状态使用各自的语义 token，避免为单个页面另配近似颜色。标签的用户自选色属于内容数据，不改变应用的主题色。

表面层级优先由留白、底色和分隔线表达。阴影用于需要区分前后层级的区域，复用主题中的轻阴影；普通内容卡片保持安静。新增渐变、材质或动效应服务于明确的层级或状态表达，并能在同类组件中统一使用。

## 字体与信息层级

使用平台适配层提供的系统字体，字重由主题控制。页面代码通过 `Text`、`Heading` 的语义变体表达层级。

| 变体 | 字号 / 行高 / 字重 | 适用内容 |
| --- | --- | --- |
| `display` | 32 / 40 / 600 | 需要突出的大标题或概览数值 |
| `heading` | 24 / 32 / 600 | 页面或面板标题 |
| `section` | 20 / 28 / 600 | 内容分组标题 |
| `body` | 16 / 24 / 400 | 正文 |
| `bodySm` | 14 / 20 / 400 | 辅助正文 |
| `label` | 14 / 20 / 600 | 字段标签与紧凑名称 |
| `button` | 16 / 20 / 600 | 按钮文字 |
| `caption` | 12 / 16 / 500 | 元信息 |

同级内容使用相同变体。通过字号、字重和间距区分层级，避免每个区域都采用最大标题。长文本应换行或按内容性质截断；操作名称和关键状态必须可读。保留共享文字组件的字体缩放能力，不通过缩小字号掩盖布局溢出。

主导航页面的标题区采用紧凑单行布局，使用 `heading` 层级，操作按钮与标题对齐。标题区自身不叠加上下留白，由页面容器和内容组间距统一控制；有常驻导航的页面缩减内容区顶部留白，为首屏正文提供更多空间。按钮仍保留共享组件的触控尺寸。

## 布局、密度与形状

- 从窄屏组织内容，再扩展到宽屏。宽屏利用最大内容宽度与导航布局组织空间，正文不随窗口无限拉宽。
- 复用 `AppShell`、`Screen` 和账户布局组件处理安全区、页面边距、滚动与键盘空间。导航断点使用 `theme.layout`，不要混用通用响应式断点。
- 间距从 `theme.spacing` 选取：相关元素靠近，独立内容组留出更大间距。同一页面保持一致的左右对齐线。
- 圆角按组件职责选用 `theme.borderRadii`：内容面板通常使用 `xl`，控件沿用共享组件定义，头像与胶囊使用 `full`。不要让所有元素使用同一种圆角。
- 交互目标以 `controlSizes.touchTarget` 为基线；输入框和主按钮复用 `field`、`primary`。视觉图标尺寸与可点击区域分别处理。
- 图标使用现有 Lucide 图标体系与主题尺寸、线宽；同类动作采用同一图标，图标按钮提供明确的可访问名称。

## 组件与状态

| 需求 | 优先复用 |
| --- | --- |
| 页面框架、导航 | `household-components.tsx`、`household-navigation.tsx` |
| 文字、按钮、输入、反馈、布局 | `primitives.tsx` |
| 主页面标题区域 | `PageIntro` |
| 设置分区面板 | `SettingsSection`，统一分组标题、图标与内容内边距 |
| 居中弹窗 | `AppDialog`，统一容器、背景、标题、关闭入口与焦点管理 |
| 表单提交与取消 | `FormActions` |
| 登录及账户布局 | `account-components.tsx` |
| 业务内容卡片 | 对应 `features/` 下的现有组件 |

新需求先通过已有组件组合实现；重复出现的视觉结构提取到共享层。业务组件负责领域内容，共享 UI 负责通用外观与状态，平台差异留在适配层。路由和业务文件引用主题值，不直接填写颜色、字号、间距或圆角常量。

### 弹窗的统一入口

新增或修改居中表单、账户面板和确认窗口时，使用 [AppDialog](../apps/client/src/ui/app-dialog.tsx)。调用方只提供标题、内容、提交状态、关闭回调和触发按钮引用；容器样式不向调用方开放覆盖。需要改变共同外观时修改基础组件，并验证所有使用场景。

`AppDialog` 统一拥有背景模糊与遮罩、最大宽度、圆角与边框、内边距、标题层级、关闭按钮、键盘避让和内容滚动；同时处理初始聚焦、Tab 循环、Esc／外部点击关闭、忙碌时禁止关闭，以及关闭后恢复焦点。背景采样由 `AppShell` 的 `DialogBackground` 提供。业务组件不再复制这些结构或独立实现另一套外壳。

锚定下拉菜单、底部选择面板和系统原生提示属于不同交互类型，不强行套用居中弹窗。确需新增类型时，先定义共享组件与适用边界，再在页面使用。

修改弹窗基础组件后，运行账户与家庭设置的 Web 回归：覆盖个人资料、退出确认、编辑和邀请窗口，并比较容器、标题、关闭按钮与模糊背景的实际渲染样式。功能测试与视觉一致性检查都需通过，不能用各页面“看起来接近”的样式替代复用。

每个可交互组件应覆盖其适用的默认、按下、选中、禁用、加载、成功和失败状态。主要操作视觉突出，次要操作层级稳定；加载时保留可识别的操作文字，避免重复提交。状态不能仅靠颜色表达。

列表、详情和表单应考虑长内容、空数据、加载与失败恢复。加载中的未知数量不能伪装成真实的零；失败后保留可恢复的输入与操作入口。视觉调整应保留既有业务语义与可访问性。

## 设计变更流程

1. 确定改动属于页面组合、组件能力还是全局主题；找到对应共享实现后再编辑。
2. 优先组合现有 token 与组件。确需新增 token 时，按用途命名，并检查是否已有等价语义。
3. 修改共享组件或主题时，检查所有受影响的使用场景，尤其是列表、编辑与账户布局，避免只让当前页面成立。
4. 若需求改变通用设计语言，在同一改动中更新本文、实现和相关检查；记录变更理由及影响范围。局部功能调整无需扩写为全局设计规则。
5. 完成下列验收后，报告实际检查结果与尚未验证的平台。

## 验收清单

- [ ] 颜色、字体、间距和圆角来自主题；同类组件的外观与状态一致。
- [ ] 主次操作清楚，页面对齐与内容密度一致；新增样式有明确用途。
- [ ] 320、390、1440 宽度下检查受影响页面：无水平溢出，导航、表单和主要操作可达。
- [ ] 检查长标题、多行文字、空数据、加载及失败场景；字体缩放后关键内容仍可操作。
- [ ] 键盘、读屏名称和状态语义可用；文字与控件对比度符合现有无障碍检查。
- [ ] 共享组件或交互变化运行相关客户端测试；布局变化运行相关 Web 检查并查看截图。对照 [UI 测试配置](../playwright.ui.config.ts) 与现有 `e2e` 用例选择覆盖范围。
- [ ] 原生布局或平台能力变化进行相应设备验收；Web 测试和打包通过不能替代真机检查。

现有 [token 检查](../apps/client/src/ui/__tests__/token-static-test.ts) 和 [对比度检查](../apps/client/src/ui/__tests__/contrast-test.ts) 是设计约束的一部分，不能为通过临时样式而降低断言。纯文档改动只需检查差异和链接。
