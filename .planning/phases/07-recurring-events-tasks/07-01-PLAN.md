<objective>
交付本阶段的示踪弹（tracer）：一条真正端到端、生产级的最薄路径 —— 用户用 `POST /api/v1/households/:householdId/tasks` 带上 `recurrence: { freq: 'daily', … }` 创建一个每日重复任务，服务端在同一个请求里写出共享的 `RecurrenceRule` 行、生成未来 90 天窗口内的全部 `Task` 发生项，随后这些发生项通过既有的 `GET .../tasks` 列表原样返回。

**用户故事（Phase 7 Goal）：** **As a** household member who manages the family schedule, **I want to** set a recurrence rule (daily, selected weekdays, weekly, monthly, or yearly) on an event or task, **so that** I don't have to manually recreate the same item over and over.

本计划只交付这条故事里最薄的一条真路径（每日 / 任务），但它必须穿透本阶段将要改动的每一层：Prisma 模型 → 手写 SQL 迁移 → 纯日期模块 → 嵌套 DTO 校验 → 生成器（含 advisory lock 与水位线）→ 既有 TasksService → 集成测试。后续所有计划都是从这条已被证明的骨架横向展开。

Purpose: 把本阶段全部架构风险（`@db.Date` 去重键、嵌套 DTO 被全局 ValidationPipe 静默剥离、池化连接下的 advisory lock、生成器幂等性）压到第一个提交里验证，而不是在十个提交之后才发现走不通。
Output: 可运行的重复任务生成链路 + 一条通过的集成测试 + 一条通过的单元测试。
</objective>

本计划只需 `walkOccurrences` 支持 `freq === 'daily'`（`interval` 生效，`endsOn`/`count`/horizon 三个终止条件都实现）；其余频率在本文件里以显式 `throw new Error('unsupported frequency')` 收口，由 07-02 补齐 —— 这是可以在不改架构的前提下填上的功能缺口，不是架构缺口。

日历游走**全部**在 `{year, month, day}` 整数三元组上完成。禁止使用 JS `Date` 的月/日分量写入器做步进 —— `new Date(2026,0,31)` 再加一个月得到的是 3 月 3 日而不是 2 月 28 日，这正是 D-09 要求钳位而非滚动的原因。整个模块里唯一构造 `Date` 的地方是 `daysInMonth` 内部的 `Date.UTC(year, month, 0)` 读取和 `localDateTimeToInstant` 的返回值。

`localDateTimeToInstant` 是本阶段**唯一**知道时区的函数（D-10）：用 `Intl.DateTimeFormat('en-US', { timeZone, timeZoneName: 'longOffset' }).formatToParts()` 取偏移，两趟修正（先按朴素 UTC 猜一次，再用猜测瞬时值处的真实偏移修正一次）。Node 24.18.0 没有全局 `Temporal`，不要使用它。

**(4) `dto/recurrence.dto.ts`** —— 沿用 `create-task.dto.ts` 的常量元组 + 中文 `@ApiProperty` 描述惯例：
`export const RECURRENCE_FREQUENCIES = ['daily','weekly','monthly','yearly'] as const;`、`RECURRENCE_WEEKDAYS = [0,1,2,3,4,5,6] as const;`、`RECURRENCE_MAX_COUNT = 1000`、`RECURRENCE_MAX_INTERVAL = 52`。

`RecurrenceDto` 字段与校验：`freq`（`@IsString() @IsIn(RECURRENCE_FREQUENCIES)`）、`interval?`（`@IsInt() @Min(1) @Max(RECURRENCE_MAX_INTERVAL)`）、`byWeekday?`（`@IsArray() @ArrayMaxSize(7) @IsInt({ each: true }) @Min(0, { each: true }) @Max(6, { each: true })`）、`startsOn`（`@Matches(/^\d{4}-\d{2}-\d{2}$/)`）、`endsOn?`（同格式）、`count?`（`@IsInt() @Min(1) @Max(RECURRENCE_MAX_COUNT)`）、`timezone`（`@IsString() @MaxLength(64)` + 自定义 `@IsIanaTimeZone()`）。若 Task 1 选中 option-a，再加 `startTimeLocal?`（`@Matches(/^([01]\d|2[0-3]):[0-5]\d$/)`）与 `durationMinutes?`（`@IsInt() @Min(0) @Max(1440)`）。

`IsIanaTimeZone` 用 `registerDecorator` 实现，内部 `try { new Intl.DateTimeFormat('en', { timeZone: value }); return true } catch { return false }`。不要把未经校验的时区字符串交给后台生成器 —— `Intl.DateTimeFormat` 对未知时区抛 `RangeError`，在 worker 里就是一个没人处理的 500（T-07-05）。

`RecurrenceResponseDto`：一行一字段风格，`id`、`freq`、`interval`、`byWeekday: number[]`、`startsOn: string`、`endsOn: string | null`、`count: number | null`、`timezone`、`materializedThrough: string | null`（外加 option-a 的两个字段）。所有日期字段输出 `YYYY-MM-DD` 而不是 `.toISOString()` —— 这是相对 `tasks.service.ts:319-341` 映射器的一处刻意偏离。

**(5) `recurrence-materializer.service.ts`** —— `@Injectable()`，构造函数注入 `PrismaService`。导出常量 `RECURRENCE_HORIZON_DAYS = 90`（A3；命名常量，不要散落字面量）、`RECURRENCE_MAX_INSTANCES_PER_RUN = 400`、`RECURRENCE_LOCK_NAMESPACE`（任一稳定 32 位整数）。

`async materializeRule(ruleId: string): Promise<number>` 全程包在 `this.prisma.$transaction(async (tx) => { … })` 里：
1. `tx.$queryRaw<Array<{ locked: boolean }>>` 取 `pg_try_advisory_xact_lock(${RECURRENCE_LOCK_NAMESPACE}, hashtext(${ruleId}))`。必须用带标签模板的 `$queryRaw` 形式（自动参数化）；本仓库此前没有任何 raw SQL 调用，这是第一处，禁止使用不做参数化的那个变体（T-07-02）。拿不到锁直接 `return 0`。
2. `tx.recurrenceRule.findUnique`，为空 `return 0`。
3. 调用 `walkOccurrences`，horizon 上界为 `today + RECURRENCE_HORIZON_DAYS`，并对结果做 `.slice(0, RECURRENCE_MAX_INSTANCES_PER_RUN)` 硬截断 —— 无论规则要求多少行（T-07-01）。
4. 每个发生日期通过 `localDateTimeToInstant` 转成 `Task.dueDate`（无时刻则本地 00:00），组装行对象：`householdId` **必须**取自规则行，绝不取自请求输入（T-07-04）；`title`/`description`/`priority`/`createdBy` 取自模板；`recurrenceRuleId` 与 `occurrenceDate` 为去重键。
5. `tx.task.createMany({ data: rows, skipDuplicates: true })` —— 幂等性靠唯一约束，不要写「先查后插」。
6. `tx.recurrenceRule.update` 推进 `materializedThrough` 到本次窗口末端（水位线，D-03）。
7. 复制关联：为每个新建实例写 `TaskAssignee` 与 `TaskLabel`，用**一个** `materializeTaskAssociations(tx, templateTaskId, newTaskIds)` 私有辅助方法集中处理，不要在多处散写复制循环。

**模型分派（本文件在本阶段的唯一入口，后续计划不再改动它的结构）**：`materializeRule` 先判断这条规则的模板行在 `tasks` 还是 `events`（各查一次 `findFirst({ where: { recurrenceRuleId: ruleId }, orderBy: { occurrenceDate: 'asc' } })`），再分派到私有的 `materializeTaskOccurrences` 或 `materializeEventOccurrences`。两个分支结构对称，都在本任务里一次写完：
- 任务分支：`dueDate = localDateTimeToInstant(occ, 规则时刻, 规则时区)`（无时刻则本地 00:00），关联复制 `TaskAssignee` + `TaskLabel`。
- 事件分支：`startTime = localDateTimeToInstant(occ, 规则时刻, 规则时区)`，`endTime = startTime + durationMinutes`。**相对时长必须恒定** —— `endTime` 由 `startTime` 加固定毫秒数得到，绝不对 `endTime` 单独再做一次日期推算（那会让跨 DST 的发生项时长被拉长或缩短一小时，违反 CONTEXT.md `<canonical_refs>`「保持相对时长不变」）。`allDay` / `location` / `description` 从模板复制，关联复制 `EventLabel`。

本计划的集成测试只端到端走任务分支；事件分支的端到端证明由 07-03 提供。这是可以在不改架构的前提下补齐的验证缺口，不是架构缺口。
