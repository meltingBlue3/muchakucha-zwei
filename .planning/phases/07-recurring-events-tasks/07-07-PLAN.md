<objective>
交付 RECR-02 的客户端一半：当用户在一个重复安排的某一次上按保存或删除时，先明确影响范围，再由服务端执行；以及让用户能分辨「这一天真的没安排」和「这一天超出了生成窗口」。

完成之后，用户可以真正取消这周二那一次而保留其余，或者从这一次起改掉整条规则 —— 并且在任何一次失败时都能确信「什么都没变」。

Purpose: UI-SPEC 的 `## SeriesScopeSheet Contract` 把触发条件、三种 mode、按钮态、默认焦点与失败行为全部定死；「范围选择先于动作」是本阶段三条体验原则之一，实现上等价于「选择前零写请求」这一条可断言的硬约束。
Output: `SeriesScopeSheet` 组件 + 两个编辑页的接线 + 两个列表页的生成窗口空态 + 覆盖零写请求与失败保持打开的组件测试。
</objective>

**(1) 触发条件。** 当且仅当当前实例 `recurrenceRuleId !== null` 时，`handleSubmit` 与 `handleDelete` 在**发出任何 API 调用之前**先打开 `<SeriesScopeSheet>`，等用户选择范围后再发请求。这是 UI-SPEC 三条体验原则之一（「范围选择先于动作」）的实现形态：**在用户选择之前不得发出任何写请求**，也不得用默认值替用户决定。

mode 映射：保存且**未改动重复规则本身** → `edit`；删除 → `delete`；保存且**改动了重复规则本身**（提交前把表单里的 recurrence 与服务端返回的原规则逐字段比对）→ `rule-change`。

**(2) 分派。** 选 `this_only`：保存走既有的 `updateEvent` / `updateTask`（直接改这一行就是「仅此一次」），删除走 `deleteEventSeries` / `deleteTaskSeries` 并带 `scope=this_only`（服务端会把任务置为 cancelled 或给事件写 cancelledAt，而不是真删行）。选 `this_and_following`：保存走 `updateEventSeries` / `updateTaskSeries`，删除走 `deleteEventSeries` / `deleteTaskSeries` 并带 `scope=this_and_following`。客户端**绝不**用多次写请求自己模拟一次拆分 —— 拆分的原子性只有服务端能保证。

**(3) 普通条目路径原样保留。** `recurrenceRuleId === null` 时保存与删除的代码路径逐字节不变，删除仍走现有的内联确认区块（不弹本弹层）。删除成功后的导航沿用现有的 `router.dismissTo(...)` 而不是 `router.back()` —— 现有注释已说明单次 pop 会落回一个已被删除的详情页。

**(4) 状态与错误。** 把提交中的 scope 传给弹层的 `submitting`；三个按钮禁用、被按下的显示 Spinner、弹层不自动关闭。成功后关闭弹层、按既有路径返回并**重新拉取权威状态**；**不做**生成数量播报（后台可能仍在补齐，报数会误导用户）；**不做**任何乐观更新。
