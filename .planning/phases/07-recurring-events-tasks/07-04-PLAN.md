**(1) `updateSeriesFromOccurrence(actorId, householdId, kind, occurrenceId, input: UpdateSeriesDto)`**（D-08 的编辑半边）。

必须用**交互式**事务 `await this.prisma.$transaction(async (tx) => { … })`。本仓库现有的数组形式 `$transaction` 无法表达这个操作 —— 第 3 步需要第 2 步返回的新规则 id。三次顺序 `await` 是错误做法：旧规则的 `endsOn` 写完之后新规则插入失败（校验、约束、连接抖动），系列就被永久截断且没有任何东西接手它。这是本阶段唯一需要交互式事务的地方，也是本仓库第一处。

事务内四步，顺序固定：
1. 旧规则 `update({ where: { id: oldRuleId }, data: { endsOn: 该发生日期减一天 } })` —— 日期减法用 `recurrence-date.ts` 的 `addDays(occurrenceDate, -1)`，在整数三元组上做，不要对 UTC 时间戳做天数加减。
2. 创建新规则：`householdId` / `createdBy` 从**旧规则行**读取（不从请求输入取，T-07-04）；`startsOn` = 该发生日期；其余字段先取旧规则值，再用 `input.recurrence` 里显式提供的字段覆盖；`materializedThrough` 置为 null（新规则尚未生成）。若旧规则用的是 `count` 终止，新规则的 `count` 需要按「已经过去的次数」扣减后写入，扣不出正数时改为不设终止条件并在 SUMMARY 中记录该判断。
3. 删除旧规则下 `occurrenceDate >= 该发生日期` 的实例行 —— **仅限尚未发生的**。已经过去的历史实例（`occurrenceDate <` 该发生日期）一行都不能碰；这是 D-08 明文要求，也是「用户已完成的家务记录不会因为改规则而消失」的唯一保证。
4. 若 `input` 带了实例字段（title/description/priority/location…），把它们写入新规则的模板行（在事务内一并创建模板实例，`occurrenceDate` = 该发生日期）。
5. 返回新规则 id。

事务**提交之后**才 `await materializer.materializeRule(newRuleId)`。不要把生成挂在拆分事务里 —— 一次慢生成会把写锁横跨整个用户请求，而仓库先例是副作用在提交后执行。

**(2) `deleteSeriesFromOccurrence(actorId, householdId, kind, occurrenceId, scope)`**。`scope === 'this_only'` 时委托给 Task 1 的 `cancelOccurrence`。`scope === 'this_and_following'` 时在同一个交互式事务里：旧规则 `endsOn` 置为该发生日期前一天、删除该日期及以后尚未发生的实例、不创建新规则。历史实例同样一行不碰。

**(3) 新建 `recurrence.controller.ts`，一个文件放两个控制器**（`labels.controller.ts` 已有同文件多控制器的先例）：
- `@Controller('households/:householdId/events/:eventId/series')` → `EventSeriesController`
- `@Controller('households/:householdId/tasks/:taskId/series')` → `TaskSeriesController`

每个控制器两条路由：`@Put()`（`operationId: 'updateEventSeries'` / `'updateTaskSeries'`，`@ApiOkResponse`，body 为 `UpdateSeriesDto`）与 `@Delete()`（`operationId: 'deleteEventSeries'` / `'deleteTaskSeries'`，`@HttpCode(204)`，`@ApiNoContentResponse`，`scope` 走 `@Query()` 并用 `@IsIn(SERIES_SCOPES)` 校验）。类装饰器沿用 `@ApiTags('recurrence')` + `@ApiBearerAuth()` + `@UseGuards(AccessTokenGuard)`。参数类沿用 `HouseholdIdParam` 加交叉类型 `& { eventId: string }`。控制器只做转发，全部业务判定在 service 里。

在 `recurrence.module.ts` 的 `controllers` 中注册这两个控制器。

**(4) 一次性条目不受影响**：`recurrenceRuleId === null` 的事件/任务不走 `/series` 路由；它们的既有 `PUT`/`DELETE` 路径逐字节不变。对这类条目调用 `/series` 返回 400 `VALIDATION_FAILED`（`codes: ['not_a_series_occurrence']`）。
